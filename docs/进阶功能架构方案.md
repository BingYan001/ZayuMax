## 0. 前置澄清：对标对象选错了

在写方案前必须先纠正一个前提，否则整份文档的方向都是错的。

**你提供的参考项目「文析助手（AsterLink）」的能力，杂鱼Max 已经全部具备且部分更强。** 逐项核对如下：

| 文析助手 README 声称的 | 杂鱼Max 现状 | 结论 |
|---|---|---|
| 16 家网盘接入，14 家支持分享解析 | 11 家（Baidu/139/GitHub/GuangYa/ILanzou/Lanzou/115/123/Quark/UC/Xunlei），**全部支持分享解析** | 数量略少，**解析覆盖率更高**（100% vs 87.5%） |
| 多网盘多账号管理 | 11 个 `*AccountEntity` + 11 个 `*AccountRepository` | **持平** |
| 统一下载管理（连接数/任务数/限速） | 分平台 `downloadThreadsFor/setDownloadThreads`，可按盘独立设并发 | **更强**（可按平台差异化，它只有全局） |
| 加密备份与恢复 | `data/backup/`（AuthBackupManager + AuthCrypto + AutoBackup + DeviceFingerprints） | **持平，且你有 AutoBackup** |
| 音视频在线播放 / 断点续播 | **无** | **落后一项** |
| 下载悬浮窗与悬浮球 | 无（有 `DownloadService`） | 落后一项（非核心） |
| — | **迅雷云端离线下载（云添加）**：`createOfflineTask` / `listOfflineTasks` / `waitOfflineTask` / BT 多文件产物 | **它有吗？文档没提** |
| — | 会话保活层 `SessionKeeper`（跨平台 Cookie 回写） | **独有** |
| — | `WebCookieJar` / `WebStorageJar` 按域清理（避免全局清罐互踢） | **独有** |
| — | `BaiduDeviceId` 设备指纹隔离 / `BaiduPendingCleanup` 延迟清理 | **独有**（风控对抗） |
| — | `HlsDownloader` / `MagnetLink` / `FastestIpDns` | **独有** |

**所以：把文析当假想敌没有意义。** 你的真实瓶颈不在"缺功能"，而在下面两处（已在 `docs/UI重构方案.md` 论证过信息架构那一处，此处补引擎侧）：

1. **引擎是"单文件最优解"，缺少任务级调度策略** —— `DownloadManager` 里 `chunkCount` / `workers` / `chunkSize` 的自适应逻辑（尾部收缩、弹性块大小、inflight 抢占）已经做得相当细，但**所有决策都局限在单任务内部**。全局层面只有 `concurrencyProvider()` 一个并发上限，没有"带宽分配"概念。
2. **风控对抗是"被动补丁式"** —— A1~A6 逐条止血（设备指纹、延迟清理、去重、降并发、errno 提示）都是**遇到问题后打的补丁**，缺少一个统一的"账号风险画像 + 主动节流"层。

本方案就围绕这两处展开，外加你点名要的功能。

## 1. 竞品缺失的进阶功能：数据流架构

### 1.1 全局跨盘聚合检索

**为什么不能实时查**：6~11 个平台并发查询，每个平台 API 往返 200ms~2s，串行要 6s+，并发则**同时触发 11 家风控**。这是自杀式设计。

**正确形态：本地倒排索引 + 后台增量刷新。**

```
┌─ 数据流 ────────────────────────────────────────────┐
│                                                     │
│  [索引构建]  (WorkManager 约束: 充电 + WiFi + 空闲)  │
│      │                                              │
│      ├─ 拉取各盘文件列表 (复用现有 *CloudViewModel  │
│      │  的 listFiles 路径，非实时，每次只刷 1 个盘)  │
│      │                                              │
│      ├─ 抽字段: name / size / mtime / path /        │
│      │   platform / accountId / fileId              │
│      │                                              │
│      └─ 写入 Room FTS4/5 虚拟表                     │
│                                                     │
│  [检索]  用户输入 → FTS MATCH → 本地返回 (毫秒级)    │
│      │                                              │
│      └─ 命中项带 platform+accountId+fileId 三元组    │
│         → 点击后走【已有的】取链流程                 │
│                                                     │
│  [兜底]  索引未命中 → 提供"联网搜索"按钮 (显式触发)  │
│          降速顺序查询 (每个平台间隔 2~5s 随机)        │
└─────────────────────────────────────────────────────┘
```

**Room FTS 表设计**（新增，不动现有任何表）：

```kotlin
@Entity(tableName = "file_index")
data class FileIndexEntity(
    @PrimaryKey val uid: String,      // platform:accountId:fileId
    val platform: String,
    val accountId: Long,
    val fileId: String,
    val name: String,                 // 用于展示
    val path: String,                 // 用于定位
    val size: Long,
    val isDir: Boolean,
    val mtime: Long,
    val indexedAt: Long               // 索引时间，用于 stale 判断
)

@Fts4(contentEntity = FileIndexEntity::class)
@Entity(tableName = "file_index_fts")
data class FileIndexFts(
    val name: String,
    val path: String
)
```

**关键工程点**：
- FTS 中文分词：Room 的 FTS4 默认 `simple` 分词器对中文按**整串**处理（"钢铁侠.mkv" 搜"钢铁"搜不到）。两个解法：① 建索引时把文件名按 bigram 切分后存入 `name` 字段；② 用 `tokenizer=icu`（需 SQLite ICU 编译支持，Android 自带 SQLite 不含）。**建议走 bigram 手动切分**，零依赖。
- 索引体积：按 10 万文件估算，每行约 200 字节 → 20MB。可接受，但需提供"仅索引文件夹名""仅索引最近 N 天"的降级选项。
- **必须显式告知用户**："这是本地索引，可能不是最新"。这是产品诚信问题，也避免误判为 bug。

### 1.2 沉浸式云媒体库

**现状**：项目**零播放能力**（`grep Player` 只命中下载器和 UC/UCCoud 的无关词）。

**架构选择**：

| 方案 | 依赖 | 优点 | 缺点 |
|---|---|---|---|
| Media3 ExoPlayer | `androidx.media3:media3-exoplayer` + `media3-ui` | 官方、字幕/音轨/倍速/断点续播全有 | +4MB，需处理多种直链协议 |
| 系统 Intent 外放 | 零 | 零成本 | 无进度记忆，体验割裂 |

**建议 Media3**，理由：你的直链是**带防盗链 Header 的临时 URL**（这正是之前 UA 对齐问题的根源），Intent 外放**无法携带 Header**，必然 403。这个技术约束直接否决了方案二。

**数据流**：

```
[媒体库页]
   │
   ├─ 数据源 = FileIndexEntity 中 isVideo/isAudio 的项 (复用 1.1 的索引!)
   │   └─ 海报：网盘缩略图接口 (115/阿里有) → 无则用文件名首帧/mime 图标
   │
   ├─ 继续观看 = PlaybackProgressEntity (新建)
   │   └─ 字段: uid, positionMs, durationMs, updatedAt, posterUrl
   │
   └─ 点击播放
       │
       ├─ 走【已有】取链流程拿 DownloadLink (含 headers!)
       │
       ├─ Media3: DefaultHttpDataSource.Factory()
       │     .setDefaultRequestProperties(link.headers)   ← 关键，链上 UA
       │     .setAllowCrossProtocolRedirects(true)
       │
       └─ ProgressUpdater 每 5s 写 PlaybackProgressEntity (节流，避免频繁 IO)
```

**边下边播**：Media3 的 `CacheDataSource` 可以直接读你的 `chunkDir` 分片 —— 但你的分片是**按 Range 乱序落盘**的（`chunkDirOf(id)`），不是线性文件。所以**不能直接复用**。要么播放走独立下载路径（另起一个顺序下载到 cache），要么等下载完成后播放。**建议先做"完成即播"**，边下边播列为 S 级后续项。

### 1.3 WebDAV 配置同步

**好消息**：项目已有 `data/backup/AuthBackupManager` + `AuthCrypto` + `AutoBackup`，**备份的序列化与加密层已经写好了**。WebDAV 只差一个"传输层"。

**不要引入 sardine-android**（它拖来 httpclient 全家桶，与 OkHttp 冲突，且你已有 OkHttp）。WebDAV 是 HTTP 的薄封装，自己写约 150 行：

```kotlin
class WebDavClient(private val client: OkHttpClient, private val base: String,
                   private val user: String, private val pass: String) {

    private fun req(method: String, path: String, body: RequestBody? = null) =
        Request.Builder()
            .url(base.trimEnd('/') + "/" + path.trimStart('/'))
            .method(method, body)
            .header("Authorization", Credentials.basic(user, pass))
            .apply { if (body != null) header("Content-Type", "application/octet-stream") }
            .build()

    suspend fun put(path: String, bytes: ByteArray) = withContext(Dispatchers.IO) {
        client.newCall(req("PUT", path, bytes.toRequestBody())).execute().use {
            if (!it.isSuccessful) error("WebDAV PUT ${it.code}")
        }
    }

    suspend fun get(path: String): ByteArray? = withContext(Dispatchers.IO) {
        client.newCall(req("GET", path)).execute().use {
            when (it.code) {
                200 -> it.body?.bytes()
                404 -> null                      // 文件不存在，非错误
                else -> error("WebDAV GET ${it.code}")
            }
        }
    }

    /** 确保目录存在：MKCOL。405/301 表示已存在，属正常 */
    suspend fun mkcol(path: String) { /* ... */ }
}
```

**同步策略（重要）**：**不要做双向自动同步**。多设备同时在线必然冲突，而冲突合并（Cookie 差异、设置项差异）是产品级难题。建议：
- **手动上传 / 手动下载**，加一个"自动备份（仅上传，覆盖式）"开关
- 文件名带设备指纹：`zayu-backup-<deviceId>.enc`，避免设备间互相覆盖
- 上传前先 `PROPFIND` 列目录，保留最近 5 份（滚动）

### 1.4 智能订阅与自动追更

**这个功能是本方案里唯一"技术可行但产品风险高"的项**，必须讲透。

**技术链路**：
```
[订阅源] 分享链接 + 文件名匹配规则 (正则/关键词)
   │
   ├─ WorkManager PeriodicWork (最短 15min，建议 6h)
   │
   ├─ 重新解析分享链接 → 拿文件列表
   │
   ├─ 与上次快照 diff (新增文件名集合 - 旧集合)
   │
   └─ 新文件 → 自动入下载队列 / 或仅通知
```

**必须先踩的坑（不写清楚会出事）**：

1. **分享链接会失效**。网盘分享链接普遍有 7~30 天有效期且可被分享者撤销。定时任务跑三天后大概率失效 —— 需要**失效通知 + 一键换链**，不能静默失败。
2. **转存成功率不是 100%**。百度/夸克对秒传和转存有严格限制，且**你已经在 A2 里为了风控把转存改成了延迟 + overwrite**。自动追更会让转存频率上升，**直接加重风控风险**。
3. **"新文件"判定会误报**。剧集重命名（`EP01.mkv` → `01.mkv`）会被判定为新文件重复下载。需要**文件名归一化**（去空格/统一大小写/剥离集数前缀后比对）。
4. **必须与防风控模式联动**。订阅任务应**强制走最低频率 + 最大延迟**，且不允许多个订阅并发执行（全局串行队列）。

**建议**：先做"**订阅 + 仅通知**"（不自动下载），观察用户实际使用 2~4 周后再开放自动下载。这既降低风控风险，也降低误报造成的浪费。

## 2. 迅雷风控对抗与限速突破：整体架构

### 2.1 先纠正需求里的三处技术误判

你需求里有三条与你的**代码事实**冲突，必须先摆平：

**❌ "多线程全连接引擎，默认96，上限1000"**

你的 `DownloadManager` 里 `MAX_INFLIGHT_CHUNKS` 是**按最大堆预算推导并封顶 512** 的（`Semaphore(MAX_INFLIGHT_CHUNKS)`）。**1000 并发在移动端必然 OOM** —— 每个 in-flight 请求持有一个 ByteArray 缓冲，1KB 缓冲 × 1000 看似不多，但 OkHttp 的连接池、响应头、拦截器链的对象开销是缓冲的 10 倍以上。

更关键：**并发数不是速度的瓶颈，CDN 的阈值才是**。你自己的注释已经写明了 —— 迅雷 CDN 对单文件并发 Range 的阈值约 8，超了会降级成 200 整文件触发 `singleStreamFallback`。**设 96 不是提速，是让任务反复归零。** 这就是为什么我把迅雷上限压在 32。

**❌ "UA 设为 `AndroidDownloadManager/11 (...)` 触发不限速通道"**

这个 UA 值本身**存疑**。`AndroidDownloadManager` 是 Android 系统自带 `DownloadManager` 的 UA，网盘 CDN **没有理由**为它开白名单通道（系统下载器对网盘而言是"盗链工具"，不是"合作方"）。

但**这不一定意味着你之前的观察是错的** —— 可能是真机上的系统下载器走了不同的**网络栈/协议参数**（如 `Accept-Encoding`、`Range` 请求头格式、TLS 指纹），而非 UA 白名单。**我已经把这三种 UA 做成了可切换档位（S1 已落地）**，真机逐档实测就能分辨是 UA 还是别的因素。

**❌ "离线下载中转，把下载转移到服务端内网"**

这条**你已经实现了**！`XunleiApi.createOfflineTask / listOfflineTasks / waitOfflineTask` + `ShareLinkParser.offlineDisplayName` —— 云添加离线下载、BT 多文件产物解析全都在。**这不是待建功能，是待优化功能**。

### 2.2 动态策略调度：触发条件与切换逻辑

这是本方案**技术含量最高**的部分，也是你真正缺的那块。

**核心洞察**：你的引擎已有精细的**任务内**自适应（尾部收缩、弹性块、inflight 抢占），但缺少**任务间**的策略层。补上这一层，收益远大于调高并发数。

```
                    ┌──────────────────────────┐
                    │  SpeedMonitor            │
                    │  滑动窗口 30s 采样 bps    │
                    └────────────┬─────────────┘
                                 │
                   ┌─────────────▼─────────────┐
                   │  StrategySelector          │
                   │  (每次采样后评估一次)       │
                   └─────────────┬─────────────┘
                                 │
   ┌─────────────────────────────┼─────────────────────────────┐
   │                             │                             │
   ▼                             ▼                             ▼
[正常直链]  ──速度 < 阈值 60%──▶ [调参重试] ──仍低──▶ [离线上中转]
   ▲                             │                             │
   │                             │  (UA切换 / 并发调整)         │
   └────速度恢复─────────────────┴─────────────────────────────┘
```

**触发条件（明确量化）**：

| 触发 | 条件 | 动作 |
|---|---|---|
| 低速判定 | 30s 滑动窗口均速 < `max(历史最优速 × 0.4, 256KB/s)`，且 `downloaded > 20MB` | 进入调参 |
| 停滞判定 | 60s 内 `downloaded` 增量为 0，且 inflight > 0 | 强制重连（换连接） |
| 降级判定 | 单请求返回 200 而非 206（Range 被忽略） | 立即切 `singleStreamFallback` |
| 提级判定 | 调参后仍低速，且当前平台支持云添加 | 建议走离线中转 |

**Kotlin 伪代码**：

```kotlin
/** 策略档位：从激进到保守，以及离线兜底 */
enum class DlStrategy { NORMAL, TUNED_UA, TUNED_CONC, OFFLINE_RELAY, GIVE_UP }

class StrategySelector(
    private val platform: String,
    private val canOfflineRelay: Boolean,          // = platform 支持云添加
    private val uaProfiles: List<XunleiUaProfile>,
) {
    private val window = ArrayDeque<Sample>()      // 滑动窗口
    private var current: DlStrategy = DlStrategy.NORMAL
    private var uaIndex = 0
    private var tunedOnce = false
    private var lastBytes = 0L
    private var stallStartMs = 0L

    /** 由 DownloadManager 的采样回调驱动 */
    fun onSample(nowMs: Long, totalBytes: Long, recentBps: Long): DlDecision {
        window.addLast(Sample(nowMs, totalBytes, recentBps))
        while (window.isNotEmpty() && nowMs - window.first().ts > 30_000) window.removeFirst()

        val avgBps = window.map { it.bps }.average().toLong()
        val bestBps = historyBestBps.get()                    // 本平台历史最优
        val lowBar = maxOf((bestBps * 4) / 10, 256L * 1024)   // 40% 或 256KB/s

        // 停滞：60s 零增量
        if (recentBps == 0L) {
            if (stallStartMs == 0L) stallStartMs = nowMs
            if (nowMs - stallStartMs > 60_000) {
                return DlDecision.Reconnect(reason = "stall_60s").also { stallStartMs = 0L }
            }
        } else stallStartMs = 0L

        if (avgBps >= lowBar) {                               // 速度达标
            if (current != DlStrategy.NORMAL) {
                current = DlStrategy.NORMAL                   // 回落，但保留已调的 UA
            }
            return DlDecision.None
        }

        // 低速，进入调整
        return when {
            uaIndex < uaProfiles.size - 1 -> {
                uaIndex++
                current = DlStrategy.TUNED_UA
                DlDecision.SwitchUa(uaProfiles[uaIndex], reason = "low_speed_${avgBps / 1024}KBps")
            }
            !tunedOnce -> {
                tunedOnce = true
                current = DlStrategy.TUNED_CONC
                DlDecision.AdjustConcurrency(workers = min(8, currentWorkers), reason = "low_speed_conservative")
            }
            canOfflineRelay -> DlDecision.SuggestOffline(reason = "all_tuning_failed")
            else -> DlDecision.None                            // 宁可不动，别自伤
        }
    }

    companion object { val historyBestBps = java.util.concurrent.atomic.AtomicLong(0) }
}
```

**★ 关键设计纪律：低速时"降并发"而不是"升并发"。**

这条反直觉，但理由在你的代码里：并发超过 CDN 阈值会导致 Range 被降级 200 → `singleStreamFallback` → **全部分片丢弃重下**（工期从"慢"变成"归零"）。所以低速时的正确动作是**回退到阈值以下（8）**，让 Range 生效。

`DlDecision` 作为 `sealed class` 返回给 `DownloadManager`，由它在任务循环里应用 —— **不要让选择器直接改引擎状态**，否则会出现跨线程竞态（你那把 `Mutex` 的经验在这里同样适用）。

### 2.3 离线中转的架构定位

```
[分享链接] ──▶ 解析拿文件列表 ──┬──▶ 直链下载 (现有主路径)
                                │
                                └──▶ 云添加离线 (§2.2 建议触发)
                                       │
                                       ├─ createOfflineTask(url, savePath)
                                       ├─ waitOfflineTask(taskId)  ← 轮询
                                       └─ 产物: 单文件给直链
                                                   BT 多文件给文件夹
                                            ↓
                                        回到【直链下载】路径取链
```

**重要认知**：离线中转**不是"绕过限速"的银弹，而是"换一条链路"**。它的真实价值有两处：
1. **BT / 磁力链接** —— 这是**唯一**可行的路径（你已经在 `ShareLinkParser` 里做了识别分流）
2. **分享链接失效前的抢救性转存** —— 不等下载完，先转存到自己帐号

对**普通 HTTP 直链**，离线中转只是把"你的带宽限制"换成"迅雷服务器到 CDN 的速度"，**末段仍要回源下载**。所以**不要把它宣传成"提速方案"**，它是"**在直链拿不到时的兜底**"。这个定位差别很重要 —— 否则用户会发现"转了一圈还是慢"，信任度下降。

## 3. 解析与下载分离：实现细节

### 3.1 你需求里这条的表述有歧义

> "带Cookie请求获取直链后，剥离Cookie，用干净的网络环境纯HTTP直链下载"

**这句话在网盘场景下是错的，照做会 403。**

**技术事实**：网盘直链的鉴权通常有两种模式：
- **URL 内嵌签名**（百度 `sign`/`timestamp`、115 `sign`、迅雷 `psign`）→ **理论上可剥离 Cookie**
- **URL + Cookie 双重校验**（夸克/UC 的 `__puus`、部分平台的防盗链 Referer）→ **剥离即失效**

你的项目里 `SessionKeeper` 明确注册了**百度 / 139 / 115** 三家 Cookie 回写，说明这三家的会话是**持续需要**的。而 `psign` 是签名字段（记忆里已明确"永远保持抓包常量"）。

**所以正确表述应该拆成两件事**：

### 3.2 正确的"分离"应拆为三层

```
① 鉴权分离（本来就该有，你已有）
   取链 = 带 Cookie + 带签名 → 产出 DownloadLink(url, headers)
   下载 = 用 DownloadLink.headers 里【冻结的】鉴权信息
   ★ 这就是上一轮修的那个 UA 对齐 bug 的同一类问题

② 会话隔离（你已有，是优势）
   WebCookieJar 按域隔离，SessionKeeper 只在 apiClient 上挂
   downloadClient 不带会话 —— 这条你本来就做对了

③ 请求特征分离（这才是"干净网络环境"的正解）
   下载请求应【模拟普通 HTTP 客户端】而非【模拟网盘 App】：
   - 不加 X-Requested-With
   - 不加 Referer（除非 CDN 要求）
   - 不加平台特有的自定义头
   - UA 用通用值
   ★ 这一点你【没有】专门做，值得补
```

**③ 的价值**：网盘风控系统会做**行为聚类**。短时间内大量"App UA + App 特有头 + 高速多线程 Range"的请求，特征极其显著。而"通用 UA + 标准 Range + 无自定义头"的请求在 CDN 日志里与普通下载工具无异，**风控权重低得多**。

**实现建议**：在 `HttpClients.downloadClient()` 上加一个拦截器，**白名单式清理头部** —— 只保留 `Range` / `If-Range` / `Accept-Encoding` / 必要的 `Referer`，其余全部剔除。这个改动很小，但对风控画像的影响很大。

## 4. 多账号 Cookie 池与随机轮询

### 4.1 你已经有 90% 的基础设施

`XunleiAccountRepository` / `BaiduAccountRepository` 等 11 个仓储 + 11 个 AccountEntity，多账号**数据结构已就绪**。缺的是**"选哪个账号"的决策层**。

### 4.2 账号健康度模型

```kotlin
/** 账号运行时健康画像（不落库，进程内内存态；重启后从 DB 里的 lastErrorAt 恢复） */
data class AccountHealth(
    val accountId: Long,
    val platform: String,
    var successCount: Long = 0,
    var failCount: Long = 0,
    var lastErrorAt: Long = 0,
    var lastErrorCode: Int = 0,          // errno / HTTP code
    var cooldownUntil: Long = 0,         // 熔断截止时间
    var reqTimestamps: ArrayDeque<Long> = ArrayDeque(),   // 用于频率控制
) {
    /** 冷却判定：按错误类型给出差异化的退避时长 */
    fun isAvailable(now: Long) = now >= cooldownUntil

    fun penaltyMs(errCode: Int): Long = when (errCode) {
        -6, -9          -> 5 * 60_000L     // 限速/风控 → 5 分钟
        -12             -> 30 * 60_000L    // 账号异常 → 30 分钟
        403             -> 10 * 60_000L
        else            -> 60_000L
    }
}
```

### 4.3 加权轮询（不是纯随机）

**纯随机会导致"坏账号被反复选中"**。正确做法是**按健康度加权**：

```kotlin
class AccountPool(
    private val clock: () -> Long = System::currentTimeMillis,
    private val rnd: Random = Random.Default,
) {
    private val health = ConcurrentHashMap<Long, AccountHealth>()

    /** 加权随机选择：健康分高者被选中概率大；冷却中的账号权重为 0 */
    fun <T : AccountRef> pick(candidates: List<T>): T? {
        val now = clock()
        // ★ 每次请求前先做频率闸门：最近 60s 内请求数超标者，权重降为 0
        val scored = candidates.mapNotNull { acc ->
            val h = health.getOrPut(acc.id) { AccountHealth(acc.id, acc.platform) }
            if (!h.isAvailable(now)) return@mapNotNull null
            val recent = h.reqTimestamps.count { now - it < 60_000 }
            if (recent >= MAX_REQ_PER_MIN) return@mapNotNull null

            val total = h.successCount + h.failCount
            val rate = if (total == 0L) 0.8 else h.successCount.toDouble() / total
            // 权重 = 成功率^2 × 新鲜度，避免老账号被榨干
            val freshness = 1.0 / (1.0 + recent)
            acc to (rate * rate * freshness)
        }
        if (scored.isEmpty()) return null
        val sum = scored.sumOf { it.second }
        var r = rnd.nextDouble() * sum
        for ((acc, w) in scored) { r -= w; if (r <= 0) return acc }
        return scored.last().first
    }

    /** 解析前随机延迟（需求里的 3~10s），★ 只对本平台串行，不是全局 sleep */
    suspend fun throttleBefore(accountId: Long) {
        val h = health.getOrPut(accountId) { AccountHealth(accountId, "") }
        val now = clock()
        val last = h.reqTimestamps.lastOrNull() ?: 0L
        val wait = (MIN_GAP_MS - (now - last)).coerceAtLeast(0L)
        if (wait > 0) delay(wait + rnd.nextLong(0, JITTER_MS))
        h.reqTimestamps.addLast(clock())
        while (h.reqTimestamps.isNotEmpty() && clock() - h.reqTimestamps.first() > 60_000) {
            h.reqTimestamps.removeFirst()
        }
    }

    fun onSuccess(accountId: Long) { health[accountId]?.let { it.successCount++; it.lastErrorCode = 0 } }

    fun onFailure(accountId: Long, errCode: Int) {
        health[accountId]?.let {
            it.failCount++; it.lastErrorCode = errCode; it.lastErrorAt = clock()
            it.cooldownUntil = clock() + it.penaltyMs(errCode)
        }
    }

    companion object {
        const val MAX_REQ_PER_MIN = 4          // 单账号每分钟最多 4 次解析请求
        const val MIN_GAP_MS = 3_000L          // 最小间隔 3s
        const val JITTER_MS = 7_000L           // 抖动 0~7s → 实际 3~10s
    }
}
```

**★ 三个必须守住的纪律**：

1. **`throttleBefore` 必须是 per-account 的，不能是全局 `delay`**。全局 sleep 会让"账号 A 在等"阻塞"账号 B 的请求"，用户体验直接崩掉。
2. **冷却状态要跨进程重启恢复**。`AccountHealth` 是内存态，但 `lastErrorAt` / `lastErrorCode` **必须落库**（加到各 `*AccountEntity`），否则用户重启一次 App 就把所有熔断清空，等于没有熔断。
3. **纯随机会失效**。需求里写"随机轮询"，但如果 3 个账号里 1 个已失效、纯随机每条请求都有 1/3 概率打空。加权轮询 + 熔断才能真正"自动跳过失效账号"。

### 4.4 防风控模式开关

需求里的"主动降速换安全"应该是一个**统一的乘数**，而不是散落各处的 if：

```kotlin
data class RiskControlProfile(
    val concurrencyCap: Int,        // 并发上限
    val minGapMs: Long,             // 解析最小间隔
    val autoRetry: Boolean,         // 是否自动重试
    val offlineRelay: Boolean,      // 是否允许云添加
) {
    companion object {
        val SAFE   = RiskControlProfile(concurrencyCap = 4,  minGapMs = 8_000, autoRetry = false, offlineRelay = false)
        val NORMAL = RiskControlProfile(concurrencyCap = 12, minGapMs = 3_000, autoRetry = true,  offlineRelay = true)
        val FAST   = RiskControlProfile(concurrencyCap = 32, minGapMs = 1_000, autoRetry = true,  offlineRelay = true)

```

`DownloadManager` 的 `effectiveWorkers` 与 `AccountPool.MIN_GAP_MS` **统一读这个 profile**。这样"防风控"开关 = 切换一个 enum，不会漏改。

```kotlin
    @PrimaryKey val id: String = "baidu",   // ← 固定字面量，非自增
    val cookie: String = "",
    val nickname: String = "",
    val updatedAt: Long = System.currentTimeMillis()
)
```

- 每个 `*AccountDao` 只有一种查询：`SELECT * FROM xxx_account WHERE id = 'xxx'`（3 个 query 全是它）
- 保存用 `@Insert(onConflict = REPLACE)` —— **登录新账号 = 覆盖旧账号**
- UI 是 `XAccountSheet` 单账号配置面板，**无账号列表、无切换、无新增**

**所以"多账号 Cookie 池 + 加权轮询"不能作为纯逻辑层加进去** ——
池子里没有第二个账号。必须**先做表结构迁移**，这使 S3 从"中"升级为"中大"，
且涉及 11 张表的 Room 迁移（数据不能丢，用户已登录的账号必须保留）。

**建议的实施路径**（按风险从低到高）：

**阶段 1（低风险，先做）**：**单账号健康度**。
不改表结构，只在 `*AccountEntity` 加 `lastErrorAt` / `lastErrorCode` / `failureCount` 三个字段。
价值：实现**跨重启的熔断**（现在重启一次所有错误状态就清零，等于没有熔断），
并在"我的"页展示健康度。「账号池管理」UI 可以先做这一版。

**阶段 2（高收益，需迁移）**：**真正的多账号**。
把 `id` 从 `"baidu"` 改为 `"baidu:<uuid>"`，加 `isActive` / `displayName` / `sortOrder` 字段，
新增 `listAll()` / `setActive()` 查询。Room 迁移时把现有行 `id` 改写为 `"baidu:<uuid>"`
（**保留原数据**，不删表重建），并加 `@Index`。
价值：这才是"多账号池"的实体。做完才能上加权轮询。

**阶段 3（依赖阶段 2）**：加权轮询 + 差异化退避（设计见 §4.3）。
`AccountHealth` 的冷却状态**必须落库** —— 这是阶段 1 已经打好的地基。

**结论：不要跳过阶段 1 直接做阶段 2。** 阶段 1 零迁移风险且立刻可用；
阶段 2 涉及 11 张表的数据迁移，一旦迁移写错，用户所有已登录账号作废 ——
这是本项目风险最高的单点，必须单独排期、单独验证。

### A.3 S3 阶段 1 的具体改动

| 文件 | 改动 |
|---|---|
| `data/account/AccountHealth.kt` | **新增**。平台无关的纯逻辑层（退避时长 / 可用性 / 加权 / 健康分）。不持状态、不碰 DB |
| 10 个 `*AccountEntity.kt` | 加 `lastErrorCode` / `lastErrorAt` / `cooldownUntil` / `failCount` / `okCount` |
| `data/db/AppDatabase.kt` | `version 19 → 20`；新增 `MIGRATION_19_20`（50 条 `ALTER TABLE ADD COLUMN`，带 DEFAULT） |
| `test/.../AccountHealthTest.kt` | **新增**。15 个用例覆盖退避/边界/加权/分值区间 |

**为什么用 ADD COLUMN 而不是重建表**：`ALTER TABLE ... ADD COLUMN ... DEFAULT` 对已有行自动填默认值，
**用户已登录的账号数据完全不受影响**。重建表要「建新表→搬数据→删旧表→改名」四步，
每步都有出错空间，而收益只是「字段顺序更整齐」—— 不值得拿用户凭证去赌。

**权重函数的三处刻意设计**（`AccountHealth.weight`）：

1. **成功率平方** —— 线性下 95% 与 80% 只差 19%，不足以让轮询明显偏向好账号；
   平方后差距拉到 40%（实测：`weight(95,5)=0.886` vs `weight(80,20)=0.631`，比值 1.405 > 线性比值 1.188）。
2. **拉普拉斯平滑** `(ok+1)/(ok+fail+2)` —— 否则新账号 1 次成功就是 100% 成功率、
   平方后权重 1.0，会瞬间挤掉所有老账号。平滑后 1 次成功只有 66%，
   样本足够时才收敛到真实值（零样本 → 0.5 中性）。
3. **权重下限 0.05** —— 全失败账号仍保留极小权重。否则「池里全是坏账号」时无账号可选，
   直接返回 null = 功能不可用。宁可试一次可能失败的，也好过告诉用户「没有可用账号」。

**`score()` 在冷却中直接返回 0**（而非只降不归零）—— 语义自洽：用户看到 0 分 + 「冷却中」标签
能立刻理解；如果显示 60 分却用不了，用户会怀疑是 bug。
